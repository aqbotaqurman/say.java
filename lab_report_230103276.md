## 4.5 Analysis

The stride sensitivity experiment did not demonstrate a sharp performance improvement at the expected 128-byte cache-line boundary.

The median execution time at stride 8 (64 bytes) was 784.8380 ms, while stride 16 (128 bytes) achieved 783.8410 ms. The difference was very small, indicating that the expected cache-line effect was not clearly visible in this measurement.

Overall, the experiment demonstrated parallel speedup but did not establish a strong false-sharing effect at the 128-byte boundary.

# 5. Phase 2 — Strong and Weak Scaling

## 5.1 Objective

Phase 2 investigated the scalability of parallel workloads using two approaches:

- Strong Scaling: The total workload remained fixed while the number of processes increased.
- Weak Scaling: The workload per process remained constant while the total workload increased.

The experiments used process counts from 1 to 8.

## 5.2 Strong Scaling Configuration

- Fixed workload: N = 1,600,000 elements.
- Process count: p = 1, 2, 3, 4, 5, 6, 7, 8.
- Serial Stage A: 5% of the workload.
- Parallel Stage B: distributed across persistent multiprocessing workers.

## 5.3 Amdahl's Law

The serial fraction was calculated as:

s = T_stageA(1) / T1strong

Measured serial fraction:

s = 0.016344

| Metric | Result |
|---|---:|
| Serial Fraction | 0.016344 |
| Theoretical Maximum Speedup | 61.1858 |
| Theoretical Speedup at 8 Processes | 7.1787 |
| Observed Speedup at 8 Processes | 3.7840 |

The theoretical maximum speedup is higher than the observed speedup because actual parallel execution includes overhead and hardware resource limitations.

## 5.4 Marginal Speedup Analysis

| Comparison | Speedup Gain |
|---|---:|
| p = 3 to p = 4 | 0.3895 |
| p = 4 to p = 5 | 0.0482 |

The marginal gain decreased by 87.63% between these two comparisons.

This indicates a significant reduction in the additional performance benefit from increasing the worker count from four to five.

The experiment does not identify the exact architectural cause because processes were not pinned to specific CPU cores.

The strong scaling experiment showed that execution time decreased from 2328.4627 ms with one process to 615.3415 ms with eight processes. The observed speedup reached 3.7840.

However, efficiency decreased to 0.4730, showing that the performance improvement was not linear.

The weak scaling experiment increased the total workload proportionally to the number of processes. At eight processes, the workload reached 2,000,000 elements, and Gustafson speedup reached 7.5196.

Weak scaling efficiency decreased to 0.4598. Execution time increased with the total workload, indicating that parallel overhead and resource limitations affected scalability.

Overall, both experiments demonstrated the benefits of multiprocessing, while also showing the limitations of ideal linear scaling.

# 6. Phase 3A — Empirical Roofline Characterization

## 6.1 Objective

The objective of Phase 3A was to measure the memory bandwidth and sustained compute performance of the test machine.

Two microbenchmarks were conducted using eight worker processes:

1. Shared-memory buffer copying to measure memory bandwidth.
2. A Python arithmetic benchmark using 16 local scalar variables to estimate sustained compute performance.

The results were used to calculate the empirical Roofline ridge point.

## 6.2 Memory Bandwidth Results

Two shared-memory buffers of 96 MB each were used.

| Parameter | Result |
|---|---:|
| Buffer Size | 96 MB each |
| Physical Workers | 8 |
| Median Time | 3.9413 ms |
| IQR | 0.5811 ms |
| Sustained Bandwidth | 48.7145 GB/s |

The measured memory bandwidth was calculated using the total read and write traffic:

BW = (2 × 96 × 10^6) / (Tmedian × 10^9)

## 6.3 Python Compute Ceiling

| Parameter | Result |
|---|---:|
| Physical Workers | 8 |
| FLOPs per Worker | 80,000,000 |
| Total FLOPs | 640,000,000 |
| Median Time | 909.4174 ms |
| IQR | 17.7342 ms |
| Compute Ceiling | 0.7037 GFLOP/s |

The compute ceiling represents the measured performance of the Python benchmark and should not be interpreted as the theoretical peak performance of the Apple M2 processor.

## 6.4 Empirical Roofline

The ridge point was calculated as:

I* = Compute Ceiling / Memory Bandwidth

| Metric | Result |
|---|---:|
| Sustained Bandwidth | 48.7145 GB/s |
| Compute Ceiling | 0.7037 GFLOP/s |
| Ridge Point | 0.0144 FLOPs/Byte |

## 6.5 Analysis

The memory benchmark achieved a sustained bandwidth of 48.7145 GB/s using eight worker processes.

The Python compute benchmark achieved 0.7037 GFLOP/s. Based on these measurements, the empirical ridge point was 0.0144 FLOPs/Byte.

These results provide an experimental reference for understanding the relationship between memory performance and computational intensity.

The compute ceiling is specific to the Python benchmark implementation. It does not represent the maximum theoretical floating-point capability of the Apple M2 CPU.

# 7. Overall Conclusion

The completed experiments provided practical insight into parallel computing performance on an Apple M2 system.

Phase 0 established the hardware configuration and calibrated the timing mechanism.

Phase 1 investigated memory stride sensitivity and process scaling. The results showed that increasing the number of processes improved execution speed, although efficiency decreased. The expected 128-byte false-sharing boundary was not clearly demonstrated.

Phase 2 compared strong and weak scaling. Strong scaling achieved an observed speedup of 3.7840 at eight processes. Weak scaling achieved a Gustafson speedup of 7.5196, although efficiency decreased as the workload increased.

Phase 3A measured sustained memory bandwidth of 48.7145 GB/s and a Python compute ceiling of 0.7037 GFLOP/s. The calculated empirical ridge point was 0.0144 FLOPs/Byte.

Overall, the experiments demonstrated that multiprocessing can improve performance, but real-world parallel applications are affected by serial work, scheduling overhead, memory behavior, and hardware resource limitations.
