## 2. Phase 1 — False Sharing and Cache-Line Contention

### 2.1 Stride sensitivity

The stride sweep was executed with 8 processes. Each slot stores a 64-bit value (8 bytes). Therefore, stride 16 corresponds to a 128-byte separation, equal to the measured cache-line size of the Apple M2.

| Stride | Separation (bytes) | Median (ms) | IQR (ms) | Throughput (Mops/s) |
|---:|---:|---:|---:|---:|
| 1 | 8 | 572.848 | 23.794 | 27.931 |
| 2 | 16 | 575.148 | 15.789 | 27.819 |
| 4 | 32 | 603.627 | 39.611 | 26.506 |
| 8 | 64 | 572.669 | 34.551 | 27.939 |
| 16 | 128 | 557.028 | 30.764 | 28.724 |
| 32 | 256 | 568.204 | 24.671 | 28.159 |

The lowest median time was measured at stride 16 (128 bytes). Compared with stride 1, it was approximately 2.76% faster. However, the difference is modest and the IQR ranges overlap, so the measurements do not show a strong, sharply defined performance drop. The 128-byte spacing is consistent with the M2 cache-line size and is the expected isolation distance for avoiding two workers writing to the same cache line.

### 2.3 Process scaling — stride 16

### 2.4 Analysis

As the number of processes increases, speedup increases, but efficiency decreases. At 8 processes, efficiency is 0.431 for stride 1 and 0.446 for stride 16. The Karp–Flatt value also increases with process count, indicating a growing effective serial/overhead component.

Stride 16 gives slightly better performance at 8 processes. This is consistent with reducing false sharing because each worker's 64-bit slot is separated by 128 bytes. Nevertheless, the measured improvement is small, so the data supports a modest benefit rather than a dramatic cache-line contention effect.

### 4.1 Empirical machine parameters

The ridge point is calculated as:

\[
I^* = \frac{P_{\text{sustained}}}{BW_{\text{sustained}}}
= \frac{0.5090}{31.9132}

\]

### 4.3 Tile footprint and operational intensity

The tile footprint is:

\[
W_{\text{tile}} = 3 \times BS^2 \times 8\ \text{bytes}
\]

The approximate tiled operational intensity is:

\[
I_{\text{tiled}} \approx \frac{BS}{12}\ \text{FLOP/byte}
\]

| BS | Tile footprint (bytes) | Operational intensity (FLOP/byte) |
|---:|---:|---:|
| 8 | 1,536 | 0.667 |
| 16 | 6,144 | 1.333 |
| 32 | 24,576 | 2.667 |
| 64 | 98,304 | 5.333 |
| 96 | 221,184 | 8.000 |
| 128 | 393,216 | 10.667 |

### 4.4 Analysis

The best blocked configuration was **BS = 96**, reaching 0.0750 GFLOP/s. Its tile footprint is 221,184 bytes (216 KiB), which is larger than the measured 64 KiB L1 data cache but smaller than the 4 MiB L2 cache.

BS = 32 has a 24 KiB footprint and fits within L1. The larger tested tiles exceed L1 but fit within L2. Increasing the block size improved the blocked implementation up to BS = 96, after which performance decreased slightly at BS = 128.

The naive Variant 1 was still the fastest overall at 0.0816 GFLOP/s. Therefore, cache blocking did not outperform the naive implementation in this particular Python benchmark. The reordered version reached 0.0766 GFLOP/s.

All measured tile intensities are above the empirical ridge point of 0.0159 FLOP/byte. Under this empirical model, the GEMM points lie to the right of the ridge point. However, these Python-loop measurements include interpreter and loop overhead; they should not be treated as the theoretical hardware peak of the Apple M2 or as a direct measurement of native floating-point throughput.

## 5. Phase 4 — Skewed Workloads and Dynamic Scheduling

### 5.1 Scheduling results

The workload used **N = 8,000** items and:

\[
K(i) = 1 + \left\lfloor \left(\frac{i}{40}\right)^2 \right\rfloor
\]

The number of worker processes was 8. The load imbalance factor is:

\[
\lambda = \frac{\max(t_{\text{worker}})}
{\frac{1}{p}\sum_{t=0}^{p-1}t_{\text{worker},t}}
\]

A value close to 1 indicates balanced worker execution.

| Strategy | Chunk size | Wall time (s) | Load imbalance λ |
|---|---:|---:|---:|
| Block Static | — | 4.1583 | 2.4280 |
| Cyclic Static | — | 2.4800 | 1.0087 |
| Dynamic Queue | 1 | 2.5410 | 1.0010 |
| Dynamic Queue | 8 | 2.5832 | 1.0053 |
| Dynamic Queue | 64 | 2.6541 | 1.0539 |
| Dynamic Queue | 512 | 3.2297 | 1.4376 |

### 5.2 Analysis

Block Static has the highest imbalance factor (2.4280). Since each worker receives one contiguous block, later blocks contain much more computational work. Some workers finish early while the worker assigned the heaviest block continues running.

Cyclic Static distributes indices across workers and achieves a much better balance (λ = 1.0087). Its wall time is 2.4800 seconds, the fastest result among all tested strategies.

For the dynamic queue, chunk size 1 gives the best balance (λ = 1.0010), but its wall time is 2.5410 seconds. The synchronized shared counter introduces coordination overhead. As chunk size increases, synchronization becomes less frequent, but load imbalance becomes more visible. At chunk size 512, wall time increases to 3.2297 seconds and λ rises to 1.4376 because large chunks leave a heavier tail of unfinished work.

The best dynamic chunk size is **C* = 1**. However, the fastest overall strategy in this experiment is Cyclic Static at 2.4800 seconds. Compared with Block Static, Cyclic Static reduces wall time by approximately 40.36%. Dynamic Queue with C = 1 reduces wall time by approximately 38.89%.

## 6. Overall Conclusion

The experiments demonstrate that parallel performance depends not only on the number of worker processes but also on memory layout, serial work, synchronization, cache capacity, and workload distribution.

In Phase 1, 128-byte spacing produced a small improvement consistent with the Apple M2 cache-line size, although the measured difference was modest. In Phase 2, adding processes improved total execution time, but efficiency declined as overheads accumulated. In Phase 3, the best blocked tile size was 96, but the naive implementation remained the fastest in this Python benchmark. In Phase 4, cyclic scheduling provided the best overall wall time, while a dynamic chunk size of 1 provided the most balanced worker activity.

The results are specific to the tested MacBook Air M2, Python 3.14.8, and the benchmark implementations. They should be interpreted as empirical measurements of these Python workloads rather than as universal hardware performance limits.
